# Bank Marketing — прогноз отклика на банковскую кампанию

Учебный ML-проект: прогнозирование того, оформит ли клиент срочный депозит по итогам телефонной кампании банка.

В проекте сравниваются Logistic Regression, Random Forest и LightGBM. Предобработка и модель объединены в `scikit-learn Pipeline`; гиперпараметры подбираются через `RandomizedSearchCV`.

**Выбранный вариант:** Random Forest на исходных признаках без `duration` и без использования созданных признаков. CV ROC-AUC — **0.7824**, test ROC-AUC — **0.7844**. Выбор сделан по CV, а не по результату на тесте.

## Задача и момент предсказания

Прогноз предполагается делать **перед конкретным запланированным звонком**, когда известны сведения о клиенте, история прошлых кампаний, дата, канал и номер текущей попытки контакта.

Модель возвращает класс и оценку вероятности открытия депозита. Возможное применение — расстановка клиентов по приоритету при ограниченном количестве звонков. Эффект такого отбора на реальную кампанию пока не измерен.

Это модель отклика: она не оценивает, насколько именно звонок увеличивает вероятность открытия депозита по сравнению с отсутствием звонка.

## Данные

Используется файл `bank.csv` из [Bank Marketing Dataset на Kaggle](https://www.kaggle.com/datasets/janiobachmann/bank-marketing-dataset), основанного на данных маркетинговых кампаний португальского банка.

[Описание исходного набора и признаков — UCI](https://archive.ics.uci.edu/dataset/222/bank+marketing).

Целевая переменная — `deposit`:

- `yes` кодируется как `1`;
- `no` кодируется как `0`.

Важно использовать указанную версию с колонкой `deposit`: варианты Bank Marketing на UCI отличаются составом данных, названием целевой колонки и разделителем CSV.

В используемом тестовом разбиении 2233 наблюдения: 1058 с открытием депозита и 1175 без него. Доля положительного класса — около 47.4%. Это характеристика данной выборки, а не оценка конверсии будущей банковской кампании.

### Какие признаки используются

| Группа | Признаки |
|---|---|
| Данные клиента | `age`, `job`, `marital`, `education`, `default`, `balance`, `housing`, `loan` |
| Предыдущие кампании | `previous`, `pdays`, `poutcome` |
| Контекст текущего контакта | `contact`, `day`, `month`, `campaign` |

`duration` исключён: длительность разговора становится известна после звонка и недоступна в выбранный момент предсказания.

В исходном описании `contact`, `day` и `month` относятся к последнему контакту текущей кампании, а `campaign` включает этот контакт. Их использование опирается на допущение, что перед оцениваемым звонком уже известны соответствующие дата, канал и номер попытки.

Для реального применения нужно подтвердить соответствие этих полей данным, доступным до звонка. Для отбора клиентов до начала всей кампании набор признаков потребуется пересмотреть.

## Схема эксперимента

1. Загрузка CSV, удаление `duration` и кодирование целевой переменной.
2. Стратифицированное разбиение на train/test в пропорции 80/20 с `random_state=42`.
3. Подбор гиперпараметров каждой модели на train: `RandomizedSearchCV`, 15 комбинаций, 3 фолда, критерий — ROC-AUC, `random_state=42`.
4. Сравнение моделей по лучшему среднему CV ROC-AUC и выбор победителя.
5. Расчёт тестовых метрик, визуализация результатов и сохранение выбранного пайплайна в `best_bank_model.pkl`.

CV ROC-AUC в таблицах — `best_score_` поиска гиперпараметров. Он используется для выбора конфигурации и не является отдельной независимой оценкой после подбора.

Тестовые результаты приведены для всех моделей; они не служат критерием выбора в итоговой схеме.

### Предобработка

- Числовые признаки: заполнение пропусков медианой и `StandardScaler`.
- Категориальные признаки: заполнение пропусков константой и `OneHotEncoder(handle_unknown="ignore")`.
- `day` обрабатывается как категориальный признак.

Предобработка находится внутри пайплайна, поэтому медианы, параметры масштабирования и категории кодировщика определяются на обучающей части каждого CV-фолда.

Единая схема используется для всех моделей: масштабирование особенно важно для Logistic Regression, а деревьям обычно не требуется.

## Проверка созданных признаков

Проверены дополнительные признаки:

| Признак | Идея |
|---|---|
| `balance_category` | Разбиение баланса на диапазоны |
| `multi_loans` | Наличие одновременно жилищного и потребительского кредита |
| `balance_per_age` | Отношение баланса к возрасту |
| `is_young_single` | Сочетание возраста до 30 лет и семейного положения `single` |
| `has_partner` | Индикатор семейного положения `married` |
| `married_with_housing` | Сочетание семейного положения `married` и жилищного кредита |

В двух запусках сохранялись исходные данные, разбиение, CV-схема, пространство и бюджет поиска гиперпараметров, а также фиксированные значения `random_state`.

Менялся набор колонок, поступающих в модель. В каждом варианте гиперпараметры подбирались заново.

| Модель | CV ROC-AUC без созданных признаков | CV ROC-AUC с созданными признаками | Разница: с − без |
|---|---:|---:|---:|
| Logistic Regression | 0.766641 | 0.769981 | +0.003340 |
| Random Forest | 0.782398 | 0.776750 | −0.005648 |
| LightGBM | 0.781060 | 0.781376 | +0.000316 |

В этом эксперименте созданные признаки немного повысили CV ROC-AUC логистической регрессии, почти не изменили результат LightGBM и снизили результат Random Forest. Лучший средний CV ROC-AUC получен без них.

Для выбранного варианта используются только исходные признаки. Разница между лучшими конфигурациями с созданными признаками и без них составляет около 0.001 ROC-AUC: этого недостаточно, чтобы утверждать устойчивое превосходство одного подхода. Проверка на повторных разбиениях пока не проводилась.

Функции генерации сохранены в `features.py` для экспериментов. В варианте без созданных признаков `get_all_feature_names()` возвращает только исходные числовые и категориальные колонки. Даже если шаг генерации остаётся в пайплайне, остальные колонки не передаются модели через `ColumnTransformer`.

## Результаты без созданных признаков

| Модель | CV ROC-AUC | Test ROC-AUC | Test F1 | Test accuracy |
|---|---:|---:|---:|---:|
| **Random Forest** | **0.782398** | 0.784440 | 0.676251 | 0.727721 |
| LightGBM | 0.781060 | 0.790629 | 0.680445 | 0.729960 |
| Logistic Regression | 0.766641 | 0.759074 | 0.645530 | 0.694581 |

Выбран Random Forest, поскольку у него максимальный CV ROC-AUC. На тесте LightGBM получил более высокие метрики, но это не меняет заранее определённый критерий выбора.

Разница CV между Random Forest и LightGBM небольшая — около 0.0013; статистическая значимость различия не установлена.

### Матрица ошибок выбранного Random Forest

Результат стандартного `predict`, без отдельного подбора порога:

| Фактический класс | Прогноз: нет депозита | Прогноз: депозит |
|---|---:|---:|
| Нет депозита | 990 | 185 |
| Депозит | 423 | 635 |

- **Precision ≈ 77.4%:** среди 820 положительных прогнозов 635 соответствуют фактическому открытию депозита в тестовой выборке.
- **Recall ≈ 60.0%:** модель обнаружила 635 из 1058 положительных случаев; 423 пропустила.
- **F1 ≈ 0.676:** сочетание precision и recall при используемом пороге.

Эти значения описывают данный тест. Они не гарантируют такую же конверсию при реальном обзвоне: результат зависит в том числе от состава клиентов и доли положительного класса.

## Интерпретация модели

Для выбранной модели рассчитывается permutation importance с ROC-AUC и 10 повторениями. В показанном эксперименте наиболее важны `month`, `contact` и `poutcome`.

Важность отражает снижение качества при перемешивании колонки. Она не доказывает причинное влияние признака на решение клиента. Например, высокая важность месяца сама по себе не доказывает, что перенос звонка на другой месяц повысит конверсию.

График рассчитывается по исходным колонкам перед всем пайплайном и не оценивает созданные признаки по отдельности. Проценты на нём — нормированные положительные средние снижения ROC-AUC, а не доли объяснённой вероятности или прибыли.

Для проверки пользы созданных признаков используется сравнение двух вариантов выше.

## Запуск

### 1. Клонирование репозитория

```bash
git clone https://github.com/TTRRYYUR/Bank-Marketing.git
cd Bank-Marketing
```

### 2. Создание виртуального окружения

```bash
python -m venv .venv
```

Активация в Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Активация в Linux/macOS:

```bash
source .venv/bin/activate
```

### 3. Установка зависимостей

```bash
python -m pip install -r requirements.txt lightgbm
```

### 4. Подготовка данных

Скачайте и распакуйте [датасет с Kaggle](https://www.kaggle.com/datasets/janiobachmann/bank-marketing-dataset).

Положите `bank.csv` с целевой колонкой `deposit` в корень проекта рядом с `main.py`.

### 5. Обучение

Запустите команду из корня проекта:

```bash
python main.py
```

Скрипт:

- обучает три модели;
- выводит таблицу метрик;
- выбирает модель по CV ROC-AUC;
- сохраняет выбранный пайплайн в `best_bank_model.pkl`;
- показывает ROC-кривые, матрицу ошибок и permutation importance.

Графики отображаются интерактивно и автоматически в файлы не сохраняются.

### Предсказание для нового клиента

Функция `predict_client` из `predict.py` принимает словарь с исходными признаками клиента и возвращает:

- `prediction` — прогноз класса;
- `probability` — оценку вероятности положительного класса.

Все 15 входных полей из таблицы признаков должны присутствовать. `deposit` и `duration` для предсказания не нужны.

Функция использует сохранённый пайплайн и кеширует загрузку модели.

## Ограничения

- Используется случайное стратифицированное разбиение. Оно не проверяет перенос качества на будущие кампании и изменения поведения клиентов со временем.
- Тестовая выборка уже просматривалась при разработке и разборе проекта. Приведённые результаты — оценка на используемой отложенной выборке; для строгого подтверждения после дальнейших изменений нужна новая независимая проверка.
- Допущение о доступности контекста звонка требует проверки на данных, сформированных до звонка.
- Калибровка вероятностей и выбор порога под стоимость ошибок пока не выполнены. Выход `predict_proba` не следует считать точно откалиброванной вероятностью без такой проверки.
- Реальная прибыль кампании не рассчитана: в проекте нет подтверждённых данных о стоимости контакта, доходе от депозита и эффекте звонка.
- Версии библиотек не зафиксированы точно, поэтому полное совпадение результатов между окружениями не гарантируется.
